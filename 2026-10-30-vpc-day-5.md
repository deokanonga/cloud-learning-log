# VPC Day 5: Security groups vs network ACLs

## The problem
Next week a web server goes into deo-lab-public-a. Only website traffic (HTTP 80, HTTPS 443) may reach it. Where do you block everything else?

## What I built
- Created a security group web-sg in deo-lab-vpc: inbound HTTP 80 and HTTPS 443 from 0.0.0.0/0, no SSH (port 22), default outbound
- Tagged the default security groups and NACLs (deo-lab-default-sg, default-vpc-sg, deo-lab-nacl, default-vpc-nacl)
- Created a custom NACL deo-lab-web-nacl with inbound 100 Allow 443 and outbound 100 Allow 443, not associated with any subnet (a planned break to test next week)
- Finished the VPC we keep for Project 3 (costs $0 to keep)

## Security group vs NACL
| | Security group | Network ACL |
|---|---|---|
| Where it sits | The server's network card (ENI) | The subnet boundary |
| Rules | Allow only | Allow and deny |
| Order | All rules checked together | Lowest rule number first, stops at first match |
| Memory | Stateful: replies go back automatically | Stateless: replies need their own rule |
| Default | Default SG: nothing in from outside | Default NACL: allows everything. New custom NACL: denies everything |

## What I learned
- Every VPC is born with a main route table, a default NACL and a default security group, and none can be deleted
- Keep the defaults safe and create one security group per job (web-sg, db-sg later)
- A port belongs to a program on a server. Firewalls read the port label on each packet; subnets have no ports
- Every packet has a From port and a To port. The visitor uses a random return port (1024-65535); the server listens on 443. The reply swaps them
- Rule numbers are only the order. Counting by 100s leaves gaps to insert rules later (like a deny at 50)
- The NACL stops at the first match, so a deny for one IP or range (like 198.51.100.0/24) must have a lower number than the allow it overrides
- Blocking IPs by hand is an emergency button; WAF and GuardDuty spot and block attackers automatically
- One outbound 1024-65535 rule covers replies for every inbound service
- SG outbound rules are for connections the server starts, not for replies
- SSH (port 22) open to 0.0.0.0/0 is a common security mistake; we will use Session Manager instead

## Breaks
| What I tried | What happens | Why |
|---|---|---|
| NACL outbound only allows 443 | Website never loads (times out) | The reply goes to the visitor's port 52000, matches no rule and falls to * Deny. Fix: outbound Allow 1024-65535 |
| Brand new custom NACL with no rules | Denies everything | Only the * Deny rule exists |
